> **当前有效决定**：逐件确认页补回「更多属性」折叠，九项属性重新可手工修改，见 §63。录入页只留照片入口，手填属性改在逐件确认页，见 §62。直连模型强度统一为高，两家都开思考，见 §61。AI 直连设置只留一个「模型」，文字分析与照片识别共用，见 §60。添置卡星光按钮与选衣生成流程见 §59，「我想要」与今日清单见 §57。搭配与添置的风格卡整图铺满，见 §56。添置主卡自动轮播同风格的三套 AI 穿搭，见 §55。添置未决生图的查询入口见 §54；今日页的最近记录见 §53；搭配与添置的轻叠卡、衣橱新版见 §52；底部导航直接切页见 §51；Android 状态栏与今日页间距见 §49。旧章节若与新章节冲突，以较新的决定为准。

## §63 逐件确认页补「更多属性」（2026-11-17 用户确认 A 方案）

**问题**：§62 删掉整表之后，**版型 / 裤长 / 正式度 / 图案 / 风格 / 季节 / 场合 / 品牌 / 备注**这九项在手机上彻底没有手工入口 —— 详情页是只读的（§33），唯一的改法是把整件「重新识别属性」交给模型重认，识别错了就只能认。

**决定**：在逐件确认的「衣物信息」面（`reviewFieldsHtml`）四个基础字段下面加一个 `<details>` 折叠，标题「更多属性」+ 小字「版型、风格、季节等」，点开是九项：

| 字段 | 形态 |
|---|---|
| 版型 / 裤长 / 正式度 / 图案 | 与主色同一套自绘选择层（原生 `select` 留在 DOM 里） |
| 风格 / 季节 / 场合 | chip 复选（`.chips` + `.chip-toggle`） |
| 品牌 / 备注 | 文本输入 |

**为什么不新写一套控件**：控件形态、`name`、词表键（`fit/length/formality/pattern/style/season/scene/brand/notes`）与 §34 那版整表逐个对齐，`readForm` / `fillForm` **一行都没改**：前者本来就按 `TEXT_NAMES / MULTI_NAMES` 遍历并跳过界面上不存在的字段，后者本来就靠 `.chips` 给词表外的旧值补可取消 chip。新写一套就等于把「保存链路」复制一份。

**为什么「颜色」不在里面**：主色已经在上面的四格里，再给一组同样的 chip 只会让人不知道哪个说了算。`colors` 多值仍由 AI 打标写、由 `readForm` 的兜底分支保留。

**卡片高度跟着翻面走**：原来卡片高度由照片面（270px 定高 + 助手条）决定，信息面只能绝对定位叠在上面 —— 内容一多就在 ~270px 的小框里内滚，「更多属性」展开 542px 根本看不成。所以翻到信息面时把两者换过来：

```css
.import-review[data-open="true"] .import-review-back  { position: relative; inset: auto; }
.import-review[data-open="true"] .import-review-front { position: absolute; inset: 0; }
```

信息面按内容撑高，整个录入面板的外层滚动条（`.wardrobe-import-scroll`）接管；收起折叠后卡片自然变矮，没有写死任何高度。

**验收（无头 Chrome 390×844，工作台演示数据）**：

- 信息面字段：`name/type/primary_color/material` + `fit/length/formality/pattern`（select）+ `style/season/scene`（chips）+ `brand/notes`（text），无缺项。
- 展开折叠：`.collapse-body` 高 542px；卡片 1137px、面板滚动区 1279 / 视口 729 —— 真的由外层接管滚动。
- 改值：勾「冬」、版型选「修身」→ 替身按钮同步显示「修身」，无报错、无横向溢出。
- 收起折叠：`display:none`；翻回照片面 `front=relative / back=absolute`，卡片回到 375px。


## §62 录入页只留照片入口（2026-11-17 用户确认 B 方案）

**决定**：录入页 `#add` 的初始态只有一张照片卡（拍照 / 相册两个按钮）+ 标题「录入 / 给衣橱添一件」。整张「手填属性 → 保存到衣橱」的表单删除。

**为什么删**：它早就不可达。

1. `web/css/features/import.css` 里 `.wardrobe-import-content .photo-form > :not(.photo-field){display:none}` 把照片字段以外的子节点全部隐藏 —— 名称、品类、主色、「更多属性」折叠块（材质/版型/裤长/正式度/图案/风格/季节/场合/品牌/备注）一律不可见、不可输入。
2. 用户一旦选了照片，`PhotoImport` 会把整个录入容器 `innerHTML` 重绘成批次视图，那份表单连 DOM 都不存在。
3. 于是「保存到衣橱」按钮只能走到 `payload.type` 为空的分支，提示「先选一个品类」—— 而界面上根本没有品类可选。

**改法**：删除 `fields.js::formHtml()`、`markup.js` 里的 `${formHtml(taxonomy)}` 与 `.form-actions` / `#add-result` / `#add-crop`，以及 `view.js` 里依附它的手填路径（`readForm`/`fillForm` 提交、AI 识别按钮、手填草稿）。`readForm`/`fillForm` 函数本身保留 —— 逐件确认面板还在用。

**手填属性去哪了**：逐件确认页的「衣物信息」面（`reviewFieldsHtml`：名称 / 品类 / 主色 / 材质）。其余属性（版型、裤长、正式度、图案、风格、季节、场合、品牌、备注）当时**只能由 AI 打标填写** —— 这一层缺口已由 §63 补上（同一张卡里的「更多属性」折叠）。

**代价**：`web/js/features/import/store.js` 的 §22 手填草稿（键 `manual`）一并下线；已存在的旧草稿记录不会被读取。

## §61 直连模型强度统一为高（2026-11-17 用户确认）

本机直连（用自己 Key 的通道）只有一档高能力模型，强度也不分档 —— 两家都按**高强度思考**发请求，界面上不加「强度」选项。

| 服务商 | 请求参数 | 实测（797KB 照片打标，同一张图） |
|---|---|---|
| OpenAI `gpt-6-luna` | `reasoning_effort: "high"` | 5.6s，reasoning 84 token（关思考 3.7s / 0 token） |
| DeepSeek `deepseek-flash` | `thinking: {"type": "enabled"}` + `reasoning_effort: "high"` | 未实测（直付余额为 0）；参数取自官方《Thinking Mode》文档，模型默认即开思考、默认档就是 high |

- 实现位置 `app/services/llm/client.py::_generation_fields()`，两条通道都生效：直连按供应商显式给；`.env` 直配（电脑当前跑的那条）对推理族模型也发 `reasoning_effort=high`，非推理族保持原样。
- 输出上限由 2048 提到 `STRONG_OUTPUT_TOKENS = 8192`（只在真的发高强度时启用）：思考与正文共用这一份额度，2048 容易被 reasoning 吃光、正文返回空串。
- **能力探测是唯一例外**：`_probe` 只有 32 token 预算，必须 `strong=False`（OpenAI `reasoning_effort: "none"`、DeepSeek `thinking: disabled`）。开着思考时预算可能被 reasoning 吃光，有的服务端还会因为预算过小而直接 400；探测只看状态码，一 400 就成了"不支持结构化输出"，静默退化到纯文本抽 JSON。
- `LLM_THINKING_DISABLED=true` 时仍按旧行为关思考（换回不认 `reasoning_effort` 的端点靠它兜底）。

验收：`pytest tests/test_llm_strength.py` 六条通过 —— 两家直连分别带 high / enabled，探测带 none / disabled 且上限仍是 32，非直连不带任何强度字段。

## §60 AI 直连设置只留一个模型（2026-11-17 用户确认）

两家服务商各只有一档高能力模型：OpenAI = GPT-6 Luna（`gpt-6-luna`），DeepSeek = V4.1 Flash（`deepseek-flash`）。文字分析和衣物照片识别**共用同一个模型**，界面上不再分「文本模型」和「图片识别模型」，也没有「暂不启用图片识别」这一档。

- 弹层字段收敛成三个：API 服务商 / API Key / 模型。切换服务商时「模型」自动换成该服务商那一档。
- 说明文案改为「选好服务商即可。文字分析和衣物照片识别用的是同一个模型。」，下方小字保留「两个服务商都只有一档高能力模型，文字分析和照片识别共用它。生成平铺图和添置款式图仍需 WorkBuddy。」
- `vision_model` 不删：后端 `profile()` 要求这个键存在、打标走视觉通道时读的也是它，所以界面用隐藏字段跟随选中模型提交（前端改 `web/js/core/ai-channel-settings.js`）。
- 老配置里 `vision_model` 为空（曾经「暂不启用」）的，由 `app/services/llm/channel.py::profile()` 归一成同一模型，升级后打标不会报「请选择图片识别模型」。

验收：工作台交互预览打开 `?mode=live#ai-models`，面板只剩两个下拉（服务商、模型）；切 DeepSeek 后模型变 `DeepSeek V4.1 Flash`、隐藏 `vision_model` 同步为 `deepseek-flash`；保存提交 `{"provider":"deepseek","model":"deepseek-flash","vision_model":"deepseek-flash","mode":"direct"}`，回到 AI 通道菜单显示「API 直连 · DeepSeek」；截图 `screens/ai-models.png` 重抓为 393×819。

## §59 选衣后生成添置推荐（2026-11-10）

添置主卡右下角的星光使用当前风格，打开两步选择。先从真实衣橱里选一件或多件（本次最多 12 件），再选一件单品、多件单品或一整套穿搭。点击「生成推荐」才提交任务。单品能分别搭配所选衣物，多件的数量由 AI 按需要在 2 至 3 件中决定。整套使用全部所选衣物和建议添置的衣物，不同穿着位置必须兼容。

整套结果展示组合平铺，下面分别列「建议添置」和「衣橱已有」。生成图标注 AI 款式示意。点「我想要」后将本组建议添置的单品和款式图一起保存，今日的「最近想要添置」可查看和取消。再次生成成功后替换当前结果，已保存单品继续留在清单里。

风格页码旁的进度入口负责恢复本轮建议，旧回看入口负责旧流程。未确认的生成用原请求号查询。款式图全部就绪后再替换上一次结果。

## §58 电脑连接自动修复

手机的「设置 → 电脑识别设置」保留电脑地址、配对码与「连接并保存」。在保存和关闭按钮之间放浅蓝色「自动修复连接」，使用表单原有状态区反馈进度和结果。

- 用户点击后先检查已保存的电脑地址。地址可用时提示连接正常。旧地址无响应时在当前 Wi-Fi 局域网查找同端口的中转。验证一台就保存新地址，验证多台时列出地址，由用户选择后再次验证。
- 修复使用现有配对码核对电脑签名，查找请求不携带配对码。更新地址时沿用现有配对和识别引擎。不调用模型或重发原任务。
- 未配对时提示先手动连接。找不到电脑时提示检查同网和电脑中转，保留原地址供手动处理。当前 Wi-Fi 网段超过 1024 个地址时限于手机所在的 /24。
- 手机与电脑中转均需更新才能使用发现功能，旧版本仍可手动连接。

## §57 添置款式的「我想要」与今日清单

添置结果中的每张款式图旁提供「我想要」。保存后按钮显示「已想要」，再次点击可取消。沿用原有添置保存记录，旧记录一并展示。新记录关联当时看到的款式图，新分析生成的相似款可单独保存。

今日页在风格卡之后、「最近搭配」之前，以两列展示全部仍想要的款式，最近添加的在前。每张卡显示图片、款式名和来源风格，点开可看推荐理由与选购要点，也可取消想要。空清单提供返回添置页的入口。浏览、保存和取消沿用已有图片与记录接口。

## §56 搭配与添置风格卡整图铺满

按确认的整卡铺图原型，照片底纹延伸到卡片四边。保留原图比例和整套衣物、鞋子与配饰，随卡片尺寸在上下或左右补齐底纹。沿用轻叠卡手势和添置主卡的三图轮播。风格名、圆点和操作图标继续叠在图片上，底部渐变保证可读。

## §55 添置审美卡内 AI 整套穿搭自动轮播

添置首页沿用轻叠卡，左右滑动或使用方向键切换审美方向。每个风格采用已确认原型中的三张通用静态 AI 示意，随应用离线提供。三张图分别呈现同风格下不同的完整穿搭，使用整齐平铺、斜向错落或层叠组合等构图。画面仅呈现衣物和配饰。

主卡稳定后首张约停留 4.3 秒，后续每 3.5 秒以约 300 毫秒的淡入切换。后卡保留上一帧。拖动或滑动过渡、打开弹层、切换页面、应用在后台、卡片离开视区时暂停。回到主卡时从该风格上次显示的图继续。系统开启「减少动态效果」时，停用自动换图。

卡内左下显示风格名和搭配圆点，右上书本打开风格说明，右下星光按该风格分析衣橱。卡片上方的页码表示当前风格，有历史记录或进行中的任务时在页码旁显示回看入口。轮播图片位于风格名、圆点和按钮下方，卡面不显示「AI 穿搭示意」标签。加载新图前保留当前图，首张图未就绪时使用该风格的静态封面。

轮播图库位于 `web/reference/purchase-lookbook/`。六张 `cover-<id>.webp` 继续作为静态风格封面使用。项目另保留 §35 的历史 AI 审美样图。

## §54 添置未决款式示意的可见恢复入口（2026-11-09）

若上一轮 AI 款式示意仍有未确认任务，新分析和补充偏好分析都不得重发生成请求。添置首页在风格页码旁提供待确认任务入口；尝试分析时，玻璃助手内明确展示未决数量与「查询原任务」按钮，查询只检查原任务。状态终结前保留该页面与入口，避免静默拦截或被全局提示遮住；确认完成后回到原分析方向。文案使用「AI 款式示意/生成」，不再使用旧搜图措辞。

查询与恢复只操作已有任务，不改衣物、草稿或已记下建议，不因点击「重新分析」而自动新建付费任务。玻璃助手内主按钮在触屏 `:hover` 与 `:active` 状态继续保持强调色，避免 Android WebView 把全局浅底悬停色套在白字主按钮上。

查询期间按钮显示「查询中」并暂停重复点击，结果或连接错误显示在助手内。离开助手后，页码旁回看入口优先打开最新已确认且还未整理成完整建议的分析。已确认部分方向时显示可查看的数量，并在助手内提供旧完整建议入口。

## §53 今日页的最近记录（2026-11-09）

风格卡片下依次放「最近搭配」和「最近记下的添置」两个独立区块。每块只预览一条记录，含缩略图、标题和已知日期，缺少记录时隐藏对应区块。搭配取最近的可用历史方案，添置取最后记下的方向，早期未记录保存日期的方向只显示「已记下」。

点卡在今日页打开对应记录的详情，关闭或返回时回到原卡位置。浏览只读已有记录和已保存的图片。

## §52 搭配与添置轻叠卡、衣橱新版（2026-11-09）

搭配与添置共用平直的轻叠卡。静止时前景卡约占卡区宽度的 91%，右侧露出一张略缩小的平行后卡。用左右拖动或方向键换风格，保留卡内标题、圆点和图标入口。

衣橱采用与其他主页面相同的标题栏，标题下显示当前列表的衣物件数。搜索、圆形筛选和蓝色录入加号同排，分类横滑。筛选用底部面板，应用后更新列表。手机采用双列圆角照片卡，名称和品类放在卡内，保留喜欢标记与衣物状态。使用共享底栏占位，录入加号沿用现有相机、相册和草稿流程。

## §51 删除页面切换圆形扩散动效（2026-11-09）

底部导航切页直接显示目标页面，移除旧页面截图、圆形扩散遮罩、排队切页和相关 CSS/资源。衣物详情、录入面板等页面内部原有的打开与关闭交互不受此决定影响。

## §50 搭配与添置的 3D 叠卡（2026-11-09）

> 本节的叠卡外观已由 §52 取代。

搭配与添置首页采用同一套 3D 叠卡。前景显示清晰的整图风格卡，右侧露出后两张缩小并倾斜的封面。后卡只作预览，前景卡显示风格名、卡内圆点及书本、星芒。搭配摘要、添置的回看入口和两页各自的弹层沿用 §48 与 §46。

左右拖动时封面跟手移动，松手后切到相邻风格，短拖回弹。六个风格首尾相接，键盘可用左右方向键。手动切换过程中不触发卡片操作，静止时由前景卡上的图标开启详情、搭配或添置分析。尊重系统的减少动画设置。

## §49 Android 状态栏与今日页留白（2026-11-09）

Android 主界面的系统状态栏使用页面底色 `#f5f5f7`，时间、电量等图标为深色。启动占位与网页加载前沿用相同背景。

手机首页加高横滑风格封面，在 393×819 视口约为 210px，并适当增加主卡和风格区之间的间距。较矮的视口缩短封面，内容较长时可滚动。首页去掉与共享底栏占位重复的下边距，保留悬浮导航、安全区和滚到底的余量。封面继续叠放风格名并整卡打开详情。

## §48 今日首页与共用风格详情（2026-11-09）

## 0. 视觉基准

2026-10-22 的 A 版沿用冷白、黑灰、蓝色，照片优先；新增悬浮磨砂玻璃底栏。具体实施与验收见 §11。

Apple（取自 `awesome-design-md/design-md/apple/DESIGN.md`）。它自己的原话最能说明：

- **"UI chrome recedes so the product can speak"** —— 界面让位给内容（我们的内容是衣服照片）
- **"no decorative gradients, no shadows on chrome"** —— 不加装饰渐变、界面不加阴影
- 唯一强调色 + 负字距 + 大留白

## 1. Design Token

| 类别 | 决定 | 为什么 |
|---|---|---|
| 强调色 | `#0066cc` **苹果蓝** | 用户拍板（原 `#2f6f4f` 绿） |
| 中性色 | `#f5f5f7` / `#1d1d1f` / `#e0e0e0` | 对齐 Apple 灰阶 |
| 字阶 | **32 / 24 / 20 / 17 / 15 / 13 / 12** | 原来只有 14px 一个基准，层次分不开 |
| 字距 | 大标题 `-0.02em`、小标题 `-0.01em` | Apple 的签名细节 |
| 间距 | **4 / 8 / 12 / 16 / 24 / 32** | 8 的倍数，改稿时心算不费劲 |
| 圆角 | **8 / 12 / 16** 三档 | 原来只有 10px 一档 |
| 阴影 | 极轻，只给真正"浮起"的元素（卡片/弹层） | Apple 原话 |

## 2. 断点

| 名称 | 宽度 | 布局 |
|---|---|---|
| **手机** | < 640px | **单列 + 底部 tab 栏** |
| 平板 / 桌面 | ≥ 640px | 顶栏导航 + **卡片网格 `auto-fill` 自适应**；内容 `max-width: 1100px` 居中 |

> ★ **v1 写的是「平板 640–1024 → 双列」，验收时推翻了。**
> 依据：两个独立来源都量到 768px 下 `.grid` 是 4 列、1024px 是 5 列，而不是 2 列。
> 而且"自适应"本来就比固定列数好 —— 照片格子的最佳列数取决于宽度，
> 写死 2 列会让平板留一大片空白。
> 修正：**不规定平板/桌面的固定列数**，由 `.grid` 的 `minmax(168px, 1fr)` 决定
> （A 版实测 390→2 列、768→4 列、1440→5 列）。手机仍是单列的那部分见 §4。

## 4. 手机端约定（重点）

- **底部 tab 栏**（A 版 72px 悬浮胶囊，见 §11）：衣橱 / 录入 / 缺口 / 搭配（=`app.js` 里 `VIEWS` 的实际顺序）
- **所有可点元素 ≥ 44×44px**（Apple HIG 的触控目标底线）
- **安全区**：底部留 `env(safe-area-inset-bottom)`（全面屏手势条）
- **页面要留出底部栏的高度**（`body { padding-bottom }`），否则滚到底时最后一段内容
  会落在固定栏底下 —— 这条**必须写在 `style.css`**，放 token 层会被 `html, body{padding:0}` 覆盖掉（踩过）
- **表单 / 详情页单列**；卡片网格是**照片格**，手机上 2 列（不是 1 列）
- 避免横向滚动；宽表用 `.tbl-wrap` 包一层
- 表单在手机上：`input` 字号 ≥ 16px（否则 iOS 会自动放大）

## 5. PWA（「装到手机上」的形态）

服务已经跑在手机里（`127.0.0.1:8787`），PWA 只差：

- [x] `manifest.webmanifest`（名称、图标、`display: standalone`、主题色）
- [x] Service Worker（离线缓存静态资源；数据靠本地服务）
- [x] 图标 192×192 / 512×512（另加 `maskable` 512 与 `apple-touch` 180）
- [ ] 手机浏览器「添加到主屏幕」后是独立图标 + 全屏 ← **待真机验证**

**缓存策略**（`web/sw.js`，刻意简单）：

| 资源 | 策略 | 为什么 |
|---|---|---|
| 外壳（HTML/CSS/JS/manifest） | **网络优先**，失败回落缓存 | 自托管要随时更新；服务在本机，网络优先几乎零代价 |
| 图片（`images` 目录） | **网络优先**，缓存只当离线兜底 | ★ **原写"缓存优先"，前提就错了**（见下） |
| API（items / outfits / health…） | **完全不拦截** | 缓存 API 会让用户看到过期衣橱 —— 最坏的一类 bug |

> ★★ **图片缓存：v1 的「缓存优先」被推翻了。**
> v1 的理由是「图片是不可变内容（文件名唯一）」—— **这个前提是假的**：
> 文件名其实是 `<单品id>.<扩展名>`（`services/images.py` 注释明说"重新上传就是覆盖"）。
> 于是换一张**同扩展名**的照片时 URL 完全不变 → 缓存永久命中旧图，
> 界面一直显示旧照片，而接口返回 200、一切"看起来成功"。**这是静默错误**：
> 用户会照着错的照片判断穿什么。
> 修正：图片改**网络优先**（服务就在本机，没有延迟代价），并把 `VERSION` 从 v1 提到 v2
> 以清掉旧缓存桶。
>
> 一般化：**选缓存策略前先确认「URL 是否真的随内容变」** —— 别拿"名字看起来唯一"当依据。

> ⚠️ **只有安全上下文能注册 SW**：`https`、`localhost`、`127.0.0.1`。
> 所以手机上用 `http://127.0.0.1:8787` 打开能装成 App，用局域网 IP
> （`http://192.168.x.x:8787`）打开**装不了** —— 浏览器规矩，不是我们的 bug。

### ★ 后端没起来时，页面得"说人话"

自托管特有的一个场景：**首页是后端自己发出来的** —— 后端没在跑时，浏览器连 HTML
都拿不到，只会显示它自己那张"无法访问此网站"的白页。用户看到那个只会觉得**坏了**，
而其实只是"后端还没启动"。

处置：SW 用**缓存里的外壳**兜底把页面渲染出来（网络优先 + 缓存回落，见上表）；
页面发现 `/health` 不通，就整页换成一张**照着做就行**的引导页
（`app.js: renderBackendDown`）—— 说清"打开 Termux 就行"，外加一个「重试」按钮。

> 这条只有在**「按需启动」**这种部署方式下才显得必要：不常驻之后，
> "打开 App 时后端还没起"是**常态**，不是异常。

### 允许的字面值（**唯一的**例外清单）

DoD 说"全部来自 token"，但下面几类**刻意保留字面值** —— 它们是**布局/几何常量**，不是视觉 token。
（清单以外出现颜色/字号/间距字面值 = 不合格。**尺寸**字面值只要属于"跟主题无关的布局常量"即可，见下。）

| 位置 | 值 | 为什么 |
|---|---|---|
| 网格最小宽度：`.grid` / `.form-grid` / `.stat-row` / `.detail` | 168 / 190 / 140 / `minmax(200px,300px)` px | 组件自身的最小宽度，与主题无关 |
| `input[type="search"]` | `min-width: 190px` | 同上（输入框的最小可用宽度） |
| ~~`bind.html` 的 `.bind-wrap` / `.qr-box` / `svg`~~ | ~~520 / 260 / 240 px~~ | §43 该页已删除，此项作废 |
| `.status .dot` | `width/height: 6px` | 一个装饰圆点 |
| 触控目标 `min-height: 44px`、`.chip-toggle>span` 的 `min-width: 44px` | 44px | 契约 §4 的硬指标，写死比绕 token 更清楚 |
| `border-radius: 50%`、`aspect-ratio: 1/1` | — | 几何关系，不是设计变量 |
| `margin: 0` / `padding: 0`、`border: 1px solid` | 0 / 1px | 归零与发丝边框 |
| 排版微调 `padding: 1px`、`vertical-align: 1px` | 1px | 发丝级视觉对齐 |
| 行高 `font: …/1.6`、`.steps { line-height: 1.9 }` | 无单位 | 相对值，不需要 token |
| `.tabbar` 的 `backdrop-filter: saturate(150%) blur(24px)` | — | A 版毛玻璃参数，保持文字与图标清晰 |
| `<meta name="theme-color">` 与 manifest 的 `theme_color` / `background_color` | `#f5f5f7` | 这两处**只能用字面值**（meta / JSON 里没有 `var()`）；值必须等于 `--bg` |
| `index.html` 里的 favicon `data:` URI | `%230066cc` | data URI 里没法用 `var()` |
| **间距工具类** `.mt-2/.mt-3/.mt-4/.mt-6/.mb-3/.pointer` | 见 `style.css` | 只给「JS 拼串里一两个元素要个间距」用；**别拿它拼布局** |

> ⚠️ `theme-color` / `theme_color` 这两处是**唯一允许重复 `--bg` 字面值**的地方，
> 改动 `--bg` 时要记得三处一起改（`tokens.css`、两个 `<meta>`、manifest）。

| 图片是"不可变内容"，SW 图片走**缓存优先** | 文件名其实是 `<单品id>.<扩展名>`，重传就是**覆盖同名文件** → URL 不变 → 永久命中旧图（而且错得**静默**） | 改**网络优先**；`VERSION` v1→v2 清旧桶 |

| `--warn: #9a6700` / `--text-faint: #86868b` | WCAG 实算 4.40 / 3.62，都低于正文要求的 4.5 | 改 `#8a5a00` / `#6b6b70`（15 组全达标） |
| 底部栏占位写在 `tokens.css` | 引入顺序改成 token 在后之后，它被 `style.css` 的 `html, body{padding:0}` **静默覆盖**（同特异性、后加载者赢） | 挪进 `style.css` 的手机段 |

原型 `docs/design/outfits-v2-preview.html`（用户先看效果图再说「可以的」）。§20 起搭配页是一张纵向长页面：审美选择器 + 介绍卡 + 生成按钮 + 结果卡 + 最近搭配 + 历史折叠。390×844 上量过——这些内容合计 **1007px，可用只有 712px**，任何排版组合都装不下「审美区 + 完整结果卡 + 底栏」，只能选牺牲哪个。用户的口径是「搭配页占住屏幕就可以，不要有往下滑的交互」，所以改成两层：

- **第一层**：一屏一张的审美卡（横向 snap，纵向滚动 **0**）。卡片 = 封面（`cover-<id>.webp`，`object-fit:cover` 撑满剩余高度）+ 名字 + 一句 core + 三个 points + 「认识这个」。**点卡本身就是生成**，页面上不再有「从衣橱生成搭配」按钮（它原来占 96px）、也不再有三页共用的审美胶囊/季节下拉。
- **第二层**：玻璃面板里堆叠的搭配卡，按住最上面那张左右拖，一张张滑走。滑走＝**翻页不是否决**（左滑下一套、右滑上一套，滑得回来）；喜欢与否仍在「依据」里提交。
- 顶部只剩一行 28px 的季节 + `1 / 6`；圆点 **44×44 按钮**里包 6px 的条（原型那个 6px 小圆点过不了 §4 的触控门禁）。

**高度账（必须三处同时成立，少一处就多出一整屏或者被底栏压住）**

1. `.outfit-view` 自己算高度：`100dvh − 顶栏(48+safe) − 上留白 16 − tabbar 72 − gap 12 − 16 − safe-bottom`（先写 `100vh` 再写 `100dvh`，老 WebView 不认 dvh 时不会退化成 auto）。桌面用 `100vh − 52 − 32×2`。
2. **父容器 `.view[data-view="outfits"]` 的 `padding-bottom` 清零**。第一版忘了这步，实测整页正好多出 **24px** 滚动（`--sp-6`）。
3. 底栏是 `fixed`，不占文档流；body 的 `padding-bottom` 已经在算高度时扣过，所以第一层**不要再给底栏留 padding**，否则重复扣。

**玻璃面板**（`aesthetic-sheet.js` 新增 `deck` / `more` 两帧，复用原有 guide/basis）

- `.aesthetic-layer.is-deck`：`padding: calc(6px + 安全区)`，面板 `height:100%`、`max-height:none` —— 整块盖住顶栏（含状态栏安全区），这是原型的口径。
- 面板里 `.aesthetic-sheet-scroll` 改成 `padding:0; overflow:hidden; flex column`，头部 54px、脚部 56px。
- 堆叠几何：`.outfit-stack-card{inset:0 0 28px}`（卡底留 28px 给露边）+ `translateY(k*38) scale(1-k*.04)` + **`transform-origin: top center`**。默认 origin 是中心，`scale` 会把后卡往上收，偏移被抵消，看起来完全没有层次 —— 原型阶段踩过一次。
- 只有最上面那张渲染完整内容；后两张是**空壳**（`is-ghost`，`pointer-events:none`）。理由有两条：露边只看得到 11–14px；带内容的副本会被 `scale` 缩成 40×40 的按钮，撞上「可点元素 ≥44」的判据。
- 拖拽阈值 86px，飞出 140% + 14°，190ms 后换页；拖完 400ms 内的 click 一律吞掉，防止松手时落进图片链接跳走。**视觉飞出方向 ≠ 翻页方向**（左滑视觉 −1、翻页 +1），第一版把两者当成一个参数，左滑直接越界失效。

**数据归属**：deck / 当前第几套 / busy / error 全部留在 `view.js`，`aesthetic-sheet.js` 只负责「什么时候重画」（`refresh(kind)`）。否则滑走一套之后会出现两份真值。

**入口收敛**：原来的「审美胶囊（选择审美）」「3 套·更多选项」两个入口随页面一起消失，能力挪进面板头部的「更多」＝ 生成设置（3/5 套、AI 比较）+ 最近搭配列表（可回看，回看后面板退回 deck 帧）。「认识这个」仍打开 guide 帧，底部按钮变成「用这个审美生成搭配」→ 在 guide 之上压一帧 deck（这时 deck 头部才有返回箭头）。试衣、依据、反馈三条链路不变。

**降级提示改成一次性 toast**：`degraded` 时不再往副标题里塞「AI 比较暂不可用…」，那句话会挤掉「第几套 / 左右拖动」这些实时信息；副标题固定为 `1 / 3 · 左右拖动换一套`。

验收（390×844，demo 库 8 件）：第一层 `documentElement` 滚动 **0**，卡 358×608（封面 356×454），圆点 700–744，底栏顶 760；面板 378×832 起于 (6,6)，堆叠区 344×688，顶卡 344×660，后卡露边 11–14px；拖一次 `1/3 → 2/3` 且文案同步；关闭后 `body` 类清空、焦点回到那张审美卡；1440×900 无滚动。门禁 `cdp_ui_check.js` 三视口 0 异常 / 0 横向溢出 / 0 触控过小。

遗留：v1 的 `.outfit-stage-*`、`.outfit-generate-bar`、`.outfit-recent-*`、`.outfit-dots`、`.aesthetic-choice-*` 等选择器**已成死代码**（只删了 JS 侧无调用的 `profileCardHtml`），建议单独一轮清；手机实机还没装机验证。

## §41 添置首页统一成一屏一张（§40 的回归修复 + 两页共用一张卡）

**起因是一次回归**：§40 重写 `aesthetic-sheet.js` 时按搭配页需要收窄了签名，删掉 `openSelector` 与它背后的 `select` 帧，**但添置页 `purchase/view.js` 的调用点没跟着改**。真机点「审美方向」报 `TypeError: sheet.openSelector is not a function`，玻璃面板根本不弹。

三道检查都没拦住，原因值得记：
- `web_assets.py` 只校验**模块 import 是否存在**，不校验对象上的**方法名**——文件在、import 通，检查就过；
- 布局探针只采**加载期** console，这个异常发生在**点击之后**；
- 四页自检只量了布局数字，**没有对 `data-*` 动作按钮逐个点一遍**。

**修法不是复原，是统一**：添置页首页原来是一个 `.style-picker`（60×87 缩略图 + 一行字，点开弹选择面板），现在换成一屏一张审美大卡，**点卡＝选定方向 + 立刻分析**（原来两步：面板里选，再点底部「按这个审美分析」）。选择面板不再需要，`openSelector` 那条调用点连同 bug 一起消失。

**卡片共用一份**：`aesthetic-ui.js` 的 `aestheticCardHtml(profile, {hint, openLabel})` + `aestheticDotsHtml(profiles, active)`，样式在 `outfits-deck.css` 的**裸类名**（`.outfit-aesthetic-card` 不挂在 `.outfit-view` 下，所以添置页直接套同一个类名）。两页只有文案不同：搭配页 `点这里生成搭配` / 添置页 `点这里分析衣橱`。`data-aesthetic-open` / `data-aesthetic-guide` / `data-aesthetic-dot` 三个属性名是全站约定，事件各页自己绑。

**★ 高度链有一处必须显式写 `flex:1`**：`page-chrome.css` 有 `.purchase-view .purchase-content{flex:0 0 auto}`，与 `.purchase-intent .purchase-content{flex:1}` **同为 (0,2,0) 且加载更晚，它赢**。不覆盖的话内容容器不收缩 → 高度由内容决定 → 卡片按封面原图比例一路撑到 **893px**，底部压住 tabbar（实测 deck 底 786 > tabbar 顶 760）。`.purchase-intent .purchase-content.is-aesthetic-home` 是 (0,3,0)，压得住，里面必须写 `flex:1;min-height:0`。

**高度账不用另算**：`.purchase-view.purchase-intent` 的 `calc()` 本来就扣掉了顶栏与 tabbar，而且它一直用 **`100vh`**（不是 `100dvh`），所以没有搭配页那个「`100dvh` 算成 0」的问题。见 §40 的高度陷阱。

**状态归属**：`aestheticIndex` 留在 `purchase/view.js`。`paint()` 会整块重建首页（`homeHtml` 变了才重建），重建后必须把 `scrollLeft` 还回去，否则「点卡 → 分析 → 收起」会跳回第一张。`restoreDeck()` 同步落一次 + rAF 再对一次。横滑的 `scroll` 监听绑在 **`root` 的 capture 阶段**——`scroll` 不冒泡，绑在 deck 元素上会随重建丢掉。

**「继续查看」入口收敛成一行**：`看分析进度 / 看本次准备 / 看上次建议` 最多同时出现两个，统一放进 `.aesthetic-home-links`（44px 一行），没有就整块不出。原来的 `.wardrobe-motif` / `.home-title` / `.body-copy` 三段为「底部对齐」服务的装饰全部撤掉——一屏一张放不下，也不需要。

验收（390×844，demo 库 7 件）：卡片 356×563，deck 121–684，圆点 684–728，tabbar 760–832，**零重叠**；`docScroll 0` / `contentOverflowY 0` / `deckSnap x mandatory`；滑到第 3 张 `idx=2` 且圆点第 3 个亮；开 guide → 关 → **`idx` 仍是 3**；点卡 → `style` 写入 `purchaseIntentStyle:v1` → 收起 → **`idx` 仍是 3、焦点回那张卡**；三视口（390/1024/1440）`overflowX 0` / `console 0` / 手机视口 `small_count 0`。

## §42 一次只出一套：模型从「挑+写」退成「只写」

**动因是用户嫌慢、费 token**，不是改产品口味。所以先量了时间花在哪，再决定改哪里。

### 实测（43 件衣橱，比 7 件演示库更接近真实）
| 项 | 改前 | 改后 | 省 |
|---|---|---|---|
| 输入 prompt | **9738 字符** | **1442 字符** | **85.2%** |
| └ 单品 JSON 行（28 件 → 3~4 件） | 6437（占 66%） | 约 700 | — |
| ├ 候选清单（12 套） | 1075 | 0（不再给候选） | — |
| └ 本地五维评估（12 套） | 1523 | 约 300（只评这一套） | — |
| 输出 | 3 条理由 ≈ 150 token | 1 条理由 ≈ 50 token | ~67% |
| 本地计算 | 327 ms | 327 ms（不变） | — |

★ **只把 `limit` 从 3 改成 1 是没用的**：`MAX_TO_LLM = 12` 写死，候选清单与单品行按 12 套算，
实测两次 prompt **一字不差（4921 字符）**。省输入必须动「送给模型什么」，不是「留几套」。

### 单套模式的链路（`limit == 1`）
1. 本地 MMR 排前 `SINGLE_POOL = 5` 套；
2. 「换一套」按**软偏好**挑：把候选按「与上一套重合几件」升序分档，只在**最不重合的一档**里随机。
   - 硬排除「共享任一件」不行：衣橱只有一双鞋时所有候选都共享它，全灭；
   - 硬排除「整套完全相同」也不行：能只换一条裤子，看着像没换；
3. 只把这 1 套的单品与评估送进模型，`_llm_rank(mode="explain")` 让模型**只写 40~60 字理由**，不排序；
4. 模型返回 `{"reason": "..."}` 或 `{"ranked":[{"reason":"..."}]}` **两种都认**（假 client 和真模型格式不一致，
   只认一种会让降级路径静默丢理由）；
5. 理由里若出现 `O1`/`A1` 这类内部代号，**丢弃**（说明它在编）。

### 前端
- `state.limit` 固定 **1**；`limit !== 1` 的代码路径保留（堆叠/拖拽/翻页都在 `bindStackDrag` 里，
  而它第一行就是 `if (deck.length < 2) return`，单卡自然不会触发）。
- 面板标题不再带「N 套」；副标题固定 `按〔审美名〕挑了 1 套`；底部按钮 `换一套`；
  「更多」里「一次生成 3/5 套」整行删除，「AI 比较」改名 **「AI 写理由」**。
- 图区列数按件数：**≤3 件一行排开、≥4 件 2×2**，用 `--cols` 传给 `.outfit-stack-grid`。
  固定 2 列时 3 件会空出第 4 格，卡片中部显空。

  之前用 `margin:auto 0` 让文字居中，单套模式下卡片高度富余，会变成上下各一个空洞，读起来像断成两截。

### ★ 顺手修的两个真 bug
1. **结果卡的 `(i)` 点了没反应**：`openBasis` 走 `open()`，而 `open()` 第一行是
   `if (disposed || !root.isConnected || entry) return;` —— 从 deck 里点 `(i)` 时面板**已经开着**，
   直接被挡掉。改成 `entry` 存在时 `push({kind:"basis"})`。这与 §41 那次回归同类：
   **方法在、签名对、但内部守卫让它永远不生效**，只有真的点一遍才发现。
2. **配件图加载失败会露出 alt 文字**：`<a>` 里的 `<img>` 挂了，浏览器渲染 alt 成蓝色带下划线的链接样子。

## §43 录入页三项收敛 + 微信入口下线（2026-11-05 用户确认）

一次会话里连着四件事，前三件是**界面手感**，第四件是**减面**。共同前提：手机 WebView 是 96
（Chromium 96），`::details-content`、`height: auto` 的过渡、`:has()` 全都不支持 —— 下面每个
做法都是被这个版本卡出来的，不是偏好。

### ① 折叠面板动画（新增 `web/js/components/collapse.js`）

原生 `<details>` 在 Chromium 96 上是**瞬间**开合，没有可用的过渡钩子。做法是把动画搬到 JS：

- 标记写 `data-fold="1"`；模块初始化时把它改成 `data-fold="ready"`，并把 `summary` 以外的子节点
  搬进包出来的 `.collapse-body`；
- `height` 在 `0 ↔ 实测像素` 之间过渡，**240ms / `cubic-bezier(.4,0,.2,1)`**，与录入弹层的曲线同源；
- 收起时**等动画走完再** `open = false`（箭头在末帧才翻），并补 `display: none`——
  只把高度压到 0 仍会留下 Tab 停点；
- `toggle` 事件兜住「代码直接改 `.open`」这条路径（草稿恢复的 `more.open = true`、
  `photo-import` 的持久化都这么干）；
- 尊重 `prefers-reduced-motion`；
- **渐进增强**：JS 没跑起来 ⇒ 没有 `.collapse-body`、没有 `ready` 标记 ⇒ 退回浏览器原生行为，
  不会出现「点不开」的死面板。

接管 6 处：`more-fields`（录入表单）/ `gp-more`（单品档案）/ `aesthetic-plan` /
`aesthetic-details` / `assistant-extra` / `detail-more`。

### ② 七个下拉改自绘选择层（新增 `web/js/components/picker.js`）

`<select>` 在手机上弹的是**系统控件**：字号、行高、分组、色彩一律不受控，21 个颜色更是一片灰。
改成底部选择层，但 **原生 `<select>` 保留在 DOM 里**，只用 CSS 藏起来（`opacity: 0;
pointer-events: none`）—— `readForm` / `fillForm` / 必填校验全走它，**保存链路一行没改**。

| 字段 | 形态 |
|---|---|
| 品类 | 51 项，按 6 个槽位（`optgroup`）分组的 2 列网格 + 搜索框 |
| 主色 | 21 色 + 「未指定」，单列，左侧 20px 色点 + 右侧名称 + 选中勾 |
| 材质 / 版型 / 裤长 / 正式度 / 图案 | 2 列文字网格，「未指定」置顶 |

选中后写 `select.value = x` 并**派发 `change`**（本项目监听的是 `change` 不是 `input`）。

★ 三处「直接赋值不发事件」必须手动补同步，否则表现为「AI 填了但按钮上还是旧值」：
`fillForm` 末尾调 `syncPickers(root)`；`clearAiFields` 后调一次；表单 `reset` 走
`MutationObserver` 之外的路径也补了。
