## 1. 产品定位

`【保留】` 与 v0.1 一致：以**个人衣橱 + 个人画像 + AI Agent** 为核心，让 AI 随长期使用逐渐理解用户，形成 Personal AI Stylist。

核心循环仍是 v0.1 第 12 节的 `Reason → Recommend → Feedback → Learn`。

**v0.2 明确一点 v0.1 没说清的**：产品的价值不在"某一次生成的搭配"，而在"**用了三个月之后，它对你的了解无法被平移到另一个产品**"。这是选址问题，详见第 14 节。

## 2. 目标用户与分发形态

`【修订】` v0.1 第 4 节说"从第一版开始就按多用户产品设计"，与实际分发形态不符。

**v0.2 的定义：**

| 项 | 定义 |
|---|---|
| 分发方式 | GitHub 开源，**每个用户自己部署一份**（照搬用户自己已经在用的模式：本地服务 + 浏览器/微信访问） |
| 「多用户」的含义 | **多实例各自部署**，不是多租户 SaaS。每个实例通常服务一个人 |
| 明确不做 | 多租户隔离、注册流程、云端图片存储、账号体系 |
| 但保留 | **所有表必须带 `user_id` 列**。成本约等于零，万一日后要支持"一家人各一份衣橱"或转 SaaS 不必重构 |

**排除的具体代价（诚实记录）**：同一实例只能一个人用。这是为了换取零成本、零合规压力、以及最低的自部署门槛。用户很清楚这笔交易。

## 3. 品类体系与槽位

`【新增】` v0.1 第 14 节列了 `category`/`subcategory` 字段，但**没有定义任何品类字典**。这是所有下游功能的地基——没有它，缺口分析算不出来、组合数算不出来、AI 打标没有输出约束。

### 3.1 六个槽位（slot）

槽位表示"一件衣服在搭配里占哪个位置"。

| 槽位 | 中文 | 说明 |
|---|---|---|
| `top` | 上装 | 基础层 |
| `bottom` | 下装 | 基础层 |
| `full` | 连身 | **自带配对的整身单品**：`dress` / `jumpsuit` / `suit`。与 top+bottom 互斥 |
| `outer` | 外套 | 可选层（穿/不穿都成立） |
| `shoes` | 鞋 | 基础层 |
| `accessory` | 配饰 | 可选层，**不参与组合数计算**（否则组合数爆炸且无意义） |

### 3.2 跨槽位品类的处理（关键决定）

| 品类 | 归入 | 理由 |
|---|---|---|
| `dress`（连衣裙）、`jumpsuit`（连体裤）、`suit`（套装） | `full` | 自带上下配对，单独构成一身 |
| `pajamas`（睡衣套装）、`loungewear`（家居服）、`activewear`（运动套装） | `full`，但**在组合数计算中按 `type` 硬排除** | 它们不该算进"能出门的组合"。**必须按 type 排除，不能按 `scene == "home"` 排除**——`scene` 是 AI 打标产出的属性，用它做过滤会引入"用未验证的字段去判断"的循环依赖 |

### 3.3 为什么 `dress` 必须是独立品类

把它拆成"上装 + 下装"会破坏组合数公式（第 6 节）。v0.2 沿用把它当独立品类的做法，代价是**组合数公式必须分两条路径相加**（见第 6 节）。

### 3.4 受控词表

- **品类**：约 55 项，覆盖中文实际场景（v0.1 未定义；西方同类项目常缺 polo/开衫/羽绒服/风衣/连体裤/家居服等中文场景品类）
- **属性词表**：颜色（22）、材质（16）、版型（6）、风格（12）、季节（4）、正式度（6）、场景（9）
- 除品类外，属性词表用于 **AI 打标的输出约束**与**用户输入的归一化**

## 4. 数据模型

`【修订】` v0.1 第 14 节给了 6 张表（User / StyleProfile / ClothingItem / Outfit / Feedback / UserPreferenceMemory）。

### 4.1 相对 v0.1 的核心改动

**改动一：`ClothingItem` 补 `slot` 与 `fit`**

- `slot` 是第 3 节的地基，没有它算不出组合数
- `fit`（版型）：v0.1 列了这个字段，但**必须真正入库、可查询**。同类开源项目里存在"schema 声明了 fit、但数据库没有这一列、也不在写入白名单里"的情况，导致它变成死字段——写入后被静默忽略，只有读原始 JSON 的代码能看到。**v0.2 明确：`fit` 是一等公民列。**

**改动二：拆出穿着记录两张表**

v0.1 只有 `Outfit`（AI 生成的方案），但第 18 节主张"知道用户真正怎么穿"。这两件事不是一回事：

| 表 | 记什么 | 层级 |
|---|---|---|
| `outfits` | AI **提议**了哪几套 | 方案 |
| `wear_events` | 用户**实际穿了**哪一整套（哪天、什么场合、天气） | 事实 |
| `item_history` | 每个单品被穿的明细，通过 `wear_event_id` 回指所属事件 | 事实（明细） |

**为什么必须要有 `wear_events` 这一层**：只有单品级历史、而整套标识可为空时，**"某天穿了哪一整套"是重建不出来的**——用户逐件记录时整套标识为空，聚合就会散架。而"预测用户今天会穿什么"恰恰依赖这个重建能力。

**改动三：`BodyProfile`** `【新增】`

v0.1 第 5.1 节要求身高/体重/身材，但数据模型里没有任何字段承载它。v0.2 补一张表。

### 4.2 完整表清单

| 表 | 用途 |
|---|---|
| `users` | 用户（单用户自用，但保留此表以承载 `user_id` 外键） |
| `clothing_items` | 衣橱单品。含受控分类（type/subtype/slot）、受控属性（颜色/材质/版型/风格/季节/正式度/场景）、打标状态、使用计数、洗护状态 |
| `outfits` | AI 生成的搭配方案 + 采纳状态 |
| `wear_events` | **穿着事实（整套）**：日期、整套单品、场合、天气、来源（AI 建议后采纳 / 自己记的） |
| `item_history` | **穿着事实（单品明细）**，回指 `wear_event_id` |
| `feedback` | 对方案的反馈：喜欢/不喜欢/换一套 + 评分（总体/舒适/风格） |
| `preference_memory` | 偏好记忆，结构化 + 条件化分桶（见第 5 节） |
| `body_profile` | 身材画像 |
| `conversation_state` | 微信会话状态（含必须回传的 `context_token`） |
| `meta` | schema 版本号，驱动自动迁移 |

**schema 版本化**：库内记录 `schema_version`，启动时按顺序执行缺失的迁移。只允许向后兼容的增量（加表/加列/加索引），不删列不改类型。

## 5. 偏好记忆：条件化衰减 + 置信度

`【推翻】` v0.1 第 14 节的 `UserPreferenceMemory` 写成自由文本：

```
用户喜欢：宽松版型 / 黑灰色 / 低饱和度 / 休闲风
用户不喜欢：紧身裤 / 过于鲜艳的颜色 / 过度正式的搭配
```

**这段散文有三个无法修补的问题**：算不了权重（"喜欢"有多喜欢？）、衰减不了（三年前的偏好和上周的一样重）、给不出置信度（一条证据和一百条证据看起来一样）。而 v0.1 第 5.3 节又说"降低该颜色的权重"——**散文和权重这两个主张互相矛盾**。

### 5.1 结构化 schema

```
preference_memory(
    user_id, tag_type, tag_value,
    context_key,        -- 条件化分桶，见 5.2
    score,              -- 原始分，-1..1（未衰减）
    evidence_count,     -- 有效样本量
    confidence,         -- 0..1
    pos_weight, neg_weight,   -- 正/负证据强度，用于算一致性
    last_updated
)
```

`tag_type` ∈ {color, style, occasion, weather, fit, material, pattern, slot, formality}

> ⚠️ **`formality` 是 W4 审查补上的**：原列表漏了它，而实现一直在用
> （`preference.tags_of_item` 会把「这套偏正式还是偏休闲」记成偏好证据）。
> 裁决为**补进规格**，而不是从实现里删掉 —— 「喜欢正式还是休闲」是真实存在的偏好维度，
> 删掉就少一条信息；而这份列表本身是封闭集合（有校验价值），所以必须补齐。

### 5.2 条件化分桶（这是本节最关键的设计）

**要解决的问题**：用户冬天不穿短袖。如果记忆不分情境，纯时间衰减会让系统把"喜欢短袖"这条记忆衰减掉——**但那不是偏好变了，是季节变了**。

**方案**：

```
context_key = "{season}|{scene}"
season ∈ {summer, winter, transition, all}
scene  ∈ {daily, work, sport, home, formal}
```

最多 20 个桶，实际常用 5–8 个，样本自然充足。

**归并规则（taxonomy 的原始取值 → 桶名）**：

| 维度 | 原始取值 | 归入桶 |
|---|---|---|
| 季节 | `spring` / `autumn` | `transition` |
| | `summer` / `winter` | 同名桶 |
| | 缺省 / 未知 | `all`（无季节上下文） |
| 场合 | `daily` / `date` / `party` / `travel` / `school` | `daily` |
| | `work` / `sport` / `home` / `formal` | 同名桶 |

> ⚠️ **场合映射为 2026-10-03 拍板**：taxonomy 定义了 9 个 scene，本节只给 5 个桶名，
> 多出来的 4 个（`date` / `party` / `travel` / `school`）按「归入日常」处理 —— 为了保住桶内样本量。
> 将来若数据表明需要拆（例如约会审美明显区别于日常），**改这一张映射表即可**，
> 分层回退会兜住拆分带来的样本不足。
> 单品的 `scene` 写进偏好表时走**同一张表**，避免 `date` 和 `daily` 两套口径并存。

**查询走分层回退**：`season|scene` → `season|all` → `all|scene` → `global`，取**首个 `evidence_count ≥ 5`** 的桶。
这样细桶样本不足时自动降级到粗桶，**不会出现"每个桶只有两条记录"**的稀碎情况。

> ⚠️ **实现口径补充（W1 定）**：回退是**逐 tag**，不是逐桶。
> 若按桶整体判断，某个桶够 5 条但恰好都是颜色类时，`style:casual` 就查不到值了。
> 改为对每个 `(tag_type, tag_value)` 各自沿回退链找 —— 黑裤子命中的是细桶、休闲风退回 `global`，各取所需。
> 链上没有达标的桶时，**取证据最多的那个而不是丢弃**：丢弃等于"没这个偏好"，
> 而实际情况是"有一点偏好但证据不足"，后者应当返回，由 `confidence` 去降权。

**关键推论**：因为季节漂移已经被 `context_key` 隔离了，**衰减函数本身不需要感知季节**。这正是分桶存在的意义。

### 5.3 衰减函数

```
w(Δt) = 0.5 ** (Δt_days / H)        H = 45 天
```

**H 的推导**：设计目标是"3 个月后权重衰减到 1/4"（即 90 天后，旧记忆只占 25% 权重）：

```
0.5 ** (90 / H) = 0.25
→ 90 / H = log(0.25) / log(0.5) = 2
→ H = 45 天   （精确解）
```

**边界校验**（说明为什么 45 是合理的而不是拍的）：

| H | 90 天后的权重 | 问题 |
|---|---|---|
| 14 天 | 1.2% | 一周就忘光，记忆剧烈抖动，无法形成稳定画像 |
| **45 天** | **25%** | 符合"三个月反映最近口味，但旧偏好仍有余温" |
| 180 天 | 70.7% | 几乎等于无衰减，三年前的偏好和上周一样重 |

### 5.4 增量更新（O(1)，不做全量重算）

新反馈进来时：极性 `r ∈ [-1,1]`（喜欢 +1 / 不喜欢 -1 / 中性 0），等效样本量 `k`：

- 显式喜欢/不喜欢：`k = 2`
- 隐式接受（用户采纳了推荐但没明确表态）：`k = 1`
- 未反馈（仅展示过）：`k = 0.3`

```
w_old = 0.5 ** (Δt / H)
score = (score * w_old * n + r * k) / (n * w_old + k)
n     = n * w_old + k
```

读接口再做一次纯投影（不改库）：

```
decayed_score = score * 0.5 ** (Δt / H)
```

**为什么用增量而不是每次全量重算**：全量重算在每年约 1000 条反馈下是 O(N) 且逐年线性增长，而增量是 O(1)。单用户场景下全量也能跑，但没必要。

### 5.5 置信度

```
confidence = (n / (n + 5)) * (0.5 + 0.5 * |decayed_score|)
```

两项各自的含义：
- `n/(n+5)` —— **样本量饱和度**：5 条 → 0.5，20 条 → 0.8，永不达到 1（不声称绝对）
- `0.5 + 0.5*|score|` —— **信号一致性**：正负证据互相抵消时（`score ≈ 0`）降到 0.5 倍

置信度的用途：作为推荐排序的权重乘子，**并直接展示给用户**（"我猜你喜欢极简风，把握 72%"），这也是第 7 节"证明越来越懂"的一部分。

### 5.6 冷启动降级

| 样本量 | 策略 |
|---|---|
| `n < 5` | 置信度压到 ≤ 0.3，**该桶不参与排序**，只用 global 桶 + 用户初始选择 |
| `5 ≤ n < 20` | 正常参与，但探索率 `ε = 0.2` |
| `n ≥ 20` | 探索率 `ε = 0.05` |

**探索机制为什么必须存在**：多轮交互式推荐的研究实测结论是"**不加探索机制的 agent 无法完成个性化**"——纯利用策略会让推荐收窄到一小撮"安全单品"，永远发现不了用户真正的偏好。代价是少数几次推荐会显得"还不懂你"，这是打破回音壁的必要成本。

## 6. 衣橱缺口分析算法

`【新增】` v0.1 第 9 节只有描述——"上装 15 件、下装 4 件、鞋 2 双 → 用户不是缺衣服，而是缺某类下装"——**没有任何算法**。v0.2 给出算法，并实算这个例子。

### 6.1 为什么必须先按季节过滤

朴素公式 `(T × B + F) × S` 有个致命失真：**20 件短袖 + 2 件羽绒服会算出很高的组合数，但冬天实际可穿组合为 0**。

**v0.2 的修正**：不做季节 key 压缩，改为逐件判定。

```python
HOME_LIKE = {"pajamas", "loungewear", "activewear"}   # 不参与"可出门组合"

usable_in(item, season) -> bool:
    if season == "all":   return True    # 「不分季节」→ 全都算可穿
    if not item.seasons:  return True    # 没标季节 = 未知 → 不排除
    return (season in item.seasons) or (len(item.seasons) >= 4)   # 只有标全四季才算通用

eff(S) = [i for i in items
          if usable_in(i, S)
          and i.type not in HOME_LIKE
          and not i.is_archived]

C(S) = eff_T * eff_B * eff_S + eff_F * eff_S
```

> ⚠️ **前两行是 W4 审查补上的**（原公式只有最后一行）。缺了它们会出真 bug：
> - `not item.seasons → True`：**没打标 ≠ 不能穿**。按 False 处理的话，刚录入、还没打标的
>   衣服会立刻从所有组合里消失、组合数变 0 —— 用户只会以为程序坏了。
> - `season == "all" → True`：`all` 既是记忆桶名、也允许当季节参数传进来。不特判的话，
>   `?season=all` 对**任何标了季节**的衣服都返回 False，静默给出 0 套，而界面写着「全部季节」。

**为什么不能用 `len(seasons) >= 3` 判定通用**：一件标了「春 + 夏 + 秋」的衣服会被误判为四季通用而并入冬天。**只有标全四季才算通用。**

### 6.2 实算 v0.1 第 9 节的例子

假设：上装 15 件、下装 4 件、鞋 2 双、连身 0 件，且都适合当前季节。

```
C = 15 * 4 * 2 + 0 * 2 = 120 套
```

**主指标就是这一个数字，而且它是可解释的**："你这季能搭出 120 套"。

### 6.3 关于"瓶颈识别"的一个诚实说明

朴素做法是算"某个槽位少一件会怎样"，取跌幅最大的槽位当瓶颈。**但在纯乘法模型里这个指标是退化的**：

```
去掉一件下装：(15 × 3) × 2 = 90   跌幅 25%
去掉一双鞋：  (15 × 4) × 1 = 60   跌幅 50%
去掉一件上装：(14 × 4) × 2 = 112  跌幅 6.7%
```

数学上，"每多一件的相对增益"恒等于 `1 / 该槽位件数`。所以**"瓶颈"必然退化成"件数最少的基础槽位"**——这不是算法的 bug，是乘法模型的性质。直接拿它当"该买什么"的建议会一直推荐"补鞋、补鞋、补鞋"，而不管那 2 双鞋是不是本来就够用。

**v0.2 的修正：建议排序改用「绝对增量 × 多样性折扣」**

```
ΔC(slot)      = 在该槽位加一件后的 C 增量
多样折扣(slot) = 该槽位已有的不同主色数 / 该槽位件数
建议分(slot)  = ΔC(slot) × 多样折扣(slot)
```

折扣的作用：**已经囤了 5 条黑裤子，再买一条黑的，组合数涨了但搭不出新感觉**——折扣会把这笔账打折。这比单纯看件数更接近"该买什么"的真实答案。

### 6.4 从 0 到 1：最小可行判定

这一条服务于冷启动（第 8 节）。`C = 0` 时，明确告诉用户缺什么才能从 0 到 1：

| 情况 | 结论 |
|---|---|
| `S = 0` | 必须有鞋，否则任何组合都不成立 |
| `T = 0` 且 `F = 0` | 缺上装或缺连身 |
| `B = 0` 且 `F = 0` | 缺下装或缺连身 |

即**最小可行集 = {1 上装, 1 下装, 1 鞋} 或 {1 连身, 1 鞋}**。

### 6.5 与同类实现的对照（为什么这个算法值得单独做）

同类开源项目里存在一种实现，是**硬编码白名单 + 比例规则**：

```python
tops    = 计数(type in ["shirt", "blouse", "t-shirt", "top"])
bottoms = 计数(type in ["pants", "jeans", "skirt", "shorts"])
if tops / bottoms > 3: 上报"上装远多于下装"
```

**它能被证明会漏判**：`sweater`、`hoodie`、`cardigan`、`jacket`、`vest` 都不在"上装"白名单里，`leggings`、`sweatpants`、`dress` 也不在"下装"白名单里。所以**一个"20 件毛衣 + 2 条裤子"的衣橱，它一个字都不会说**。

v0.2 的算法天然避免这个问题（受控词表 + 槽位），并且**保留了旧规则的判定结果作为对照项**——文档和产品里都能看到"旧规则会怎么说、我们会怎么说"。

## 7. 可证伪指标

`【新增】` 这一节回答 v0.1 第 21 节的**问题 B：AI 怎样证明自己越来越懂用户？**

**v0.2 的原则**：**声称与测量必须成对出现。** 第 14 节声称"最了解某个用户"，这一节就必须给出测量方法；否则第 14 节只是营销文案。

### 7.1 三级指标

| 级别 | 指标 | 定义 | 数据来源 |
|---|---|---|---|
| 一级 | 采纳率 | 被采纳的方案数 / 有响应的方案数 | 本地直接算 |
| 一级 | 平均评分 | 总体 / 舒适 / 风格三个维度 | 反馈表 |
| 二级 | **Top-1 采纳率** | 一次给 3 套，用户选了排第 1 的那套的比例 | 需埋点记录展示顺序 |
| 二级 | 换一套率 | 用户点"换一套"的比例 | 需埋点 |
| 三级 | **偏好预测准确率** | 用前半段反馈训练偏好，预测后半段用户的选择，算命中率 | 需累积足够样本 |

### 7.2 基线与显著性（必须写死，否则指标不可用）

| 项 | 值 | 说明 |
|---|---|---|
| **随机基线** | **33%** | 给 3 套选 1 套，瞎猜就是 1/3。**低于或接近 33% 的准确率等于"没有更懂"** |
| 最小样本量 | **20 条反馈** | 少于 20 条时准确率噪声极大，**该指标不展示、不参与任何决策** |
| 有效阈值 | **> 50%** | 显著高于随机基线，才认为个性化真的在起作用 |

### 7.3 指标展示的硬性要求

三级指标的趋势**必须能在产品里看到**。这是 v0.1 第 21 节问题 B 的答案落地方式——如果用户看不到这些数字，那"AI 越来越懂我"就永远只是一个说法。

## 8. 冷启动与最小可用衣橱

`【推翻】` v0.1 第 21 节把最小闭环定义为：

> 录入**一件**衣服 → AI 理解 → 问一次穿搭 → 从自己的衣橱找到组合 → 用户反馈 → 画像更新

**这个闭环在数学上不成立**：一件衣服搭不出整套。`C = 0`。

### 8.1 v0.2 的门槛定义

**不用"件数"定义门槛，改用"可用性"定义**：

> **门槛 = AI 能给出至少 1 套用户不否决的搭配。**

**为什么不用件数**：如果定成"6 件（2 上装 + 2 下装 + 2 鞋 = 8 种组合）"，问题在于**组合总数 ≠ 可用搭配数**——2 件互不搭的上装和下装，组合出来是废的。而判断"搭不搭"恰恰是产品要做的事，用它自己来定义自己的门槛，是循环定义。

用"一次真实会话能否得到不否决的搭配"来定义，则门槛是可实测的：**发一次请求，看用户是否否决**。

### 8.2 首次会话的设计

不要求用户先攒够衣橱，而是直接进入循环：

```
录入少量单品
  → 立刻给出一套（哪怕只有 3 件）
  → 用户反馈（喜欢 / 不喜欢 / 换一套）
  → 偏好写入记忆
  → 提示"再补一件，你的选择会翻倍"
  → 回到第一步
```

**依据**：多轮交互式推荐的研究实测，系统通常能在 **4–5 轮**内锁定用户的偏好风格（例如识别出"偏爱裙子多过牛仔裤"）。所以冷启动的解不是"先录 20 件衣服"，而是"**第一次对话就进入反馈循环**"。

## 9. 录入动机机制

`【新增】` 这一节回答 v0.1 第 21 节的**问题 A：为什么用户愿意持续录入衣服？**

v0.1 说"需要让录入本身具有价值"，但没有给方案。v0.2 给两个具体机制：

### 9.1 组合数即时反馈

每次成功录入一件单品，**在响应里立刻返回**：

```
你的可选搭配从 12 套变成 20 套
```

这是把"录入"这个体力活**换算成可感知的收益**。数字来自第 6 节的 `C(当季)` 前后对比。

### 9.2 基于该单品的现有搭配

录入完成后立刻给一条**用这件新衣服 + 你已有的衣服**组成的搭配。用户立刻看到"它已经能用了"，而不是"我还得录完整个衣柜才有用"。

### 9.3 辅助动机：闲置可见

从没穿过的单品列表（"你有 7 件从没穿过"）。利用的是沉没成本焦虑——这是同类产品里被验证有效的动机，成本也极低（一个 SQL 查询）。

### 9.4 批量导入的失败语义

`【新增】` 补一处**规格缺口**（2026-10-03 定稿）。

**背景**：P1 阶段微信（P3）与网页（P2）都还没做，而缺口分析**少于 20 件没有意义**——所以要有一个"一次喂一批"的入口 `POST /items/bulk`。但 `clothing_items` 上有一个唯一索引：

```sql
CREATE UNIQUE INDEX idx_items_hash ON clothing_items(user_id, image_hash)
    WHERE image_hash IS NOT NULL
```

**问题**：一批 20 件里有 1 件撞了这个索引，怎么办？

**决定：跳过并回报清单，不做整体回滚。**

理由：
- 导入是**补数据的体力活**。一件重复不该让另外 19 件白干——整体回滚会逼用户先找出是哪一件、改完再重跑整批。
- 但**必须逐件回报**。只返回一个"成功 19 件"、不说少的是哪件，那就变成了**静默失败**，比直接报错更糟。

**输出契约**（对应 `models.py` 的 `BulkItemsOut`）：

| 字段 | 含义 |
|---|---|
| `total` / `created` / `skipped` / `failed` | 计数 |
| `outcomes[]` | **逐件**结果：`index`（原始序号）/ `name` / `status` / `reason` |
| `combination_delta` | 沿用 §9.1——一次导入也要能让用户看到回报 |

**三种状态的分工**：

| status | 含义 | 是不是错误 |
|---|---|---|
| `created` | 入库成功 | — |
| `skipped` | **预期内的重复**（`image_hash` 撞唯一索引） | ❌ 不是 |
| `failed` | 其他原因（字段非法等） | ✅ 是 |

**为什么 `skipped` 和 `failed` 必须分开**：前者是正常情况（用户很可能重复导同一份文件），后者是异常。混在一起会让用户以为系统有问题。

**明确定不做的**：不加 `?atomic=true` 开关。批量导入是单人自用的补数据操作，多一个分支就多一条要维护和测试的路径，收益不值。

## 10. AI 架构：让 LLM 只做「排序 + 解释」，不做「生成」

`【修订】` v0.1 第 13 节提出了正确的约束（"推荐结果应基于数据库中的 item_id"），但只停在"系统再确认这些衣服确实属于当前用户"。**这是事后校验，不是结构保障。**

### 10.1 结构性根治

```
本地枚举合法组合（从数据库真实单品生成候选）
        ↓
LLM 只负责：重排候选 + 写推荐理由
        ↓
返回的 item_id 必然是本地生成过的，模型没有编造的机会
```

**对比"提示词约束 + 事后校验"**：

| | 提示词约束 | 本地枚举 + LLM 只排序 |
|---|---|---|
| 幻觉风险 | 依赖模型自觉，会失效 | **结构上不可能** |
| 校验成本 | 每次都要校验并处理失败 | 不需要 |
| 模型能力要求 | 需要较强的指令遵循 | 只需要判断力和语言能力 |

### 10.2 受控词表的喂法与归一化

AI 打标必须输出受控词表内的值。**豆包 / DeepSeek / 其他 OpenAI 兼容接口对结构化输出的支持程度不一致**，所以必须有降级链：

```
json_schema（最强约束）
  ↓ 不支持则退
json_mode
  ↓ 不支持则退
纯文本 + 正则抽取 JSON
  ↓ 无论走哪条
输出后强制归一化：别名匹配 → 包含匹配 → 认不出就进 `unresolved`（**不写库**）
```

**归一化层不可省略。** 模型可能输出"黑色"而不是 `black`、"T 恤"而不是 `tshirt`——这些都必须能被吸收。

> ⚠️ **归一失败的处置是 W4 审查补上的**。原文写的是"落到 `other`"，但那只对 `type` 成立
> （`slot` 由 `type` 派生，所以 `other` 有意义）；对 `color` / `material` / `fit` 这类字段，
> **根本没有 `other` 这个取值**。
>
> 实现采用更保守的语义：**认不出的值既不写库、也不编一个出来，而是进 `unresolved` 返回给前端**，
> 由用户在界面上手选。理由与「宁缺勿脏」一致 —— 少一个字段不会出事，
> 但库里多一条没法统计的脏值会污染缺口分析和偏好统计，而且是**静默**的。
>
> 另一条相关裁决（W4）：打标认不出 `type` 时**不许覆盖已有的分类**。
> 否则一件「上装」会被降级成「配饰」，直接掉出组合计算 —— 打标失败不该破坏已有数据。

### 10.3 上下文裁剪（几百件衣服不能全塞进去）

三步：

1. **SQL 硬过滤**：按季节、未归档筛掉大部分（300 件 → 40~80 件）
2. **本地打分取前 K≈25 件**：按 `Σ(decayed_score × confidence)` 排序
3. **紧凑编码 + 短别名**：每件压成一行（约 40 字符），并分配别名 `A1..A30`，返回后映射回真实 ID

> ⚠️ **第 1 步原本还写着"按正式度"硬过滤 —— 那是错的，2026-10-03 裁决去掉。**
> 同属规格的 §6.1 写着「formality 只在生成阶段做软过滤」，与本条**直接矛盾**。
> 裁决为**软过滤**（只影响排序、不淘汰候选），理由：衣橱尺寸小的时候硬筛容易把候选筛空、
> 甚至给出 0 套 —— 新用户看到"0 套搭配"只会以为程序坏了；而"软过滤 + 排序"能达到同样效果。

```
A1|top|黑|棉|宽松|极简|夏,秋|日常
A2|bottom|藏蓝|牛仔|常规|休闲|春,秋,冬|日常
```

**短别名的双重好处**：省 token，且**大幅降低模型抄错 ID 的概率**（让它复述 32 位 UUID 是自找麻烦）。

### 10.4 多样性

避免"3 套看起来差不多"。用 MMR（最大边际相关）贪心重排：

```
pick = argmax[ λ * score(方案) − (1−λ) * max_{已选} Jaccard(方案, 已选) ]
λ = 0.7
```

再叠加两条硬约束：**3 套中至少 2 套主色不同、至少 2 套正式度不同**。

### 10.5 供应商无关

抽象为 `LLMClient` / `VisionClient` 两个接口，实现一个 `OpenAICompatClient` 即可覆盖 OpenAI / DeepSeek / 豆包 / 本地推理服务。配置项：`LLM_BASE_URL`、`LLM_API_KEY`、`LLM_MODEL`、`VISION_MODEL`。

**打标模型与生成模型分开配置**（两者对能力的要求不同：打标要视觉，生成要判断力）。

## 14. 核心壁垒

`【推翻】` v0.1 第 18 节主张核心壁垒是"个人衣橱数据 + 长期行为数据 + 个性化画像"。

### 14.1 v0.1 想解决的问题是对的

它回答的是：**这个产品凭什么不被抄、凭什么用户不换？**

推理链是：功能没有门槛（同一个大模型谁都能调）→ 护城河必须转移到别人拿不到的东西上 → 用户私有、随时间累积、需要投入劳动才能形成的数据 → 转换成本。

这个目的服务三件事：**防御**（防被模型能力碾压）、**留存**（给"越用越好"一个经济学解释）、**估值**（锚在数据资产而非功能清单）。

**目的完全正确，不要删。要换的是载体。**

### 14.2 但 v0.1 的论证有三个隐含前提，破了两个

| 前提 | 含义 | 在本方案下 | 被什么打掉 |
|---|---|---|---|
| A. 数据归你 | 你控制存储与 schema | 破了 | 用户自托管，数据在各自机器上 |
| B. 你能横向聚合 | N 个用户的衣橱放在一起可沉淀风格知识 | **破了（最致命）** | **自托管天然反聚合**，每个实例是孤岛 |
| C. 用户搬不走 | 数据难导出、转换成本高 | 勉强 | 结构化数据可随时导出 |

**前提 B 是关键**：数据壁垒的经济学基础是"规模聚合"——数据越多越值钱，是因为能横向比对。而自托管与聚合在根上互斥。**这不是实现问题，是模式与论证的互斥。**

### 14.3 v0.2 的替代论证：壁垒在「机制」

| | v0.1 | v0.2 |
|---|---|---|
| 载体 | 数据 | **机制** |
| 论证 | 数据在我这儿 → 用户离不开 | **机制在我这儿 → 用户离不开** |

**为什么机制能成立**：连续使用三个月后，偏好权重、置信度、穿着历史、被否决过的搭配，全都长在系统里。换一个产品的代价不是"迁移数据"，而是**从零开始被重新认识一遍**。转换成本成立，而且**不需要聚合任何人的数据**。

**具体的三块机制**（即 v0.2 的差异化所在）：

1. **条件化衰减 + 置信度**的偏好记忆（第 5 节）
2. **季节化组合覆盖率**的缺口分析（第 6 节）
3. **微信入口**的交互设计——穿搭是"早上出门前 30 秒"的场景，比打开网页快得多

### 14.4 一个反直觉但重要的反向论证

**SaaS 会伤害"最了解某个用户"这个目标。**

一旦要求用户把整个衣橱的照片上传到别人的服务器，大量用户只会传一部分、或者干脆不传。**数据不全，AI 就永远不可能"最了解"他。**

结论：**自托管是达成目标的前置条件，不是妥协。**

### 14.5 「最了解」必须可测

第 14 节声称了目标，第 7 节就必须给出测量方法。**声称与测量成对出现，缺一个都让这一节退化成营销文案。**

## 15. 技术栈与部署

`【新增】` v0.1 完全没有技术栈。

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | Python 3.13 | SQLite 是标准库（零依赖）；LLM/视觉生态成熟；数据模型与同类项目同语言便于参考 |
| Web 框架 | FastAPI + uvicorn | 自带交互式 API 文档，P1 阶段可以直接当调试台用 |
| 数据库 | **SQLite（标准库 sqlite3）** | 单文件、零安装、零配置。数据规模：几百件衣服 + 每年约 1000 条穿着记录，三年不到 2 万条，全量读入内存是毫秒级 |
| 前端 | 后端同源静态页，不引框架 | 定位是"能看衣橱 + 能改 AI 打标错的标签 + 能看缺口分析"，不需要构建链 |
| 图片 | 本地文件目录 | 单用户场景，不需要对象存储 |
| 模型 | 任意 OpenAI 兼容接口 | 见 10.5 |

**为什么不用 Postgres / Redis / Docker**：那是多用户 SaaS 级设施的答案。单用户自用场景引入它们，只会让**别人把项目跑起来**这件事从"一条命令"变成"先装一堆东西"——而分发门槛是这类工具能不能被用的第一道关。

### 15.1 自部署方式（面向未来的其他用户）

```
git clone <repo>
pip install -r requirements.txt
python run.py
```

浏览器打开本地端口即可。微信入口可选接入。

### 15.2 数据可迁移性

- 全部数据在一个 SQLite 文件里，拷贝即备份
- schema 版本化 + 自动迁移，升级版本不会丢数据
- 提供导出接口（JSON），用户随时可以拿走自己的数据

**注意**：这一条与第 14 节的壁垒论证不冲突——**用户能拿走数据，但拿不走已经长在系统里的偏好权重和置信度**。

## 16. MVP 范围

`【修订】` v0.1 第 15 节列了 7 项 MVP。v0.2 收敛为按阶段交付：

| 阶段 | 内容 | 完成标志 |
|---|---|---|
| P0 | 服务能起来 | 健康检查通过、API 文档可打开 |
| P1 | 后端完整 | 批量导入 ≥20 件 → 缺口分析 → 组合数 → 记穿着 → 写反馈 → 偏好记忆更新，全部跑通 |
| P2 | 本地网页 | 浏览器完成全部核心操作，AI 打标错了能在页面上改 |
| **P3** | **微信入口** | **项目终点**：微信里发照片 → 自动打标 → 问「这件怎么搭」→ 给出搭配 → 回「这套行」记反馈 |

### 第一版暂时不做

`【保留】` v0.1 第 16 节的清单，并补充：

- 电商商品实时搜索、购买链接、自动购物车
- 虚拟试穿、生成真人模特
- **全衣柜一次识别**（v0.1 已排除，v0.2 维持——逐件录入 + 用户确认是数据质量的前提）
- 品牌合作、社交社区、穿搭分享
- 多租户 SaaS、账号体系、云端图片存储
- 复杂推荐算法、大规模模型训练

**第一版最重要的是证明**（v0.1 第 16 节的判断，保留）：

> 用户愿意把自己的衣服交给 AI，并且愿意持续使用 AI 帮自己做穿搭决策。

## 17. 路线图

`【修订】` v0.1 第 17 节的四阶段演进（AI 衣橱助手 → 个人 AI Stylist → Personal Fashion Agent → 商业化）。

**v0.2 的处置**：
- Phase 1 / 2 / 3 保留（衣服识别 + 问答 → 加画像与反馈 → 加主动提醒与缺口分析）
- **Phase 4（商业化：品牌推荐 / 电商 / 商城 / 会员 / Pro）标记为「与当前路线不兼容」**

理由：商业化 Phase 4 的前提是平台方掌握用户数据并能运营流量，而这与第 14 节确立的"自托管是达成目标的前置条件"直接冲突。**如果哪天真的要做 Phase 4，必须先承认第 14 节的论证要重写**，而不是悄悄地滑过去。
