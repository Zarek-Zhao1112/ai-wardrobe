# P3 微信闭环 · 实现设计

> **用途**：P3 的实现依据。产品级规格在 `设计文档_v0.2.md` §11/§13；
> 协议细节在 `ilink-protocol.md`。本文只写"**怎么实现**"。
>
> **P3 = 项目终点**（用户确认的"做出来"标准）：
> 微信里发消息 → 给出搭配 → 回「这套行」记反馈。

---

## 1. 范围：分两段，别一次赌两件没验过的事

| | 场景 | 依赖 | 风险 |
|---|---|---|---|
| **第一版** | A 问搭配 · C 文字录入 · E 没得搭了 | 微信通道 | ✅ 只赌"协议能不能通" |
| 第二阶段 | B 发照片打标 | 视觉 key **+** CDN 媒体 AES 解密 | ⏸ 两个**都没验证过**的风险 |

**为什么分开**：图片那条路上有两个独立的不确定项（视觉模型是否可用、CDN 加密是否解得对）。
一起做的话出问题时分不清是哪个。第一版跑通就证明"协议通了"，第二版只需专注媒体。

**顺带**：iLink 的语音消息**自带转文字**（`voice_item.text`），第一版就接上 ——
"早上出门前 30 秒"的场景里，说话比打字快。成本几乎为零。

## 2. 分层：通道 / 会话 / 业务，三层不许互相认识

```
微信 ──► app/channels/clawbot.py ──► app/services/conversation.py ──► 业务
         （协议层）                    （会话状态机）                （既有的
                                                                     recommend /
                                                                     tagging /
                                                                     wardrobe …）
```

| 层 | 认识什么 | **不认识**什么 |
|---|---|---|
| `channels/clawbot.py` | iLink 协议、token、长轮询、`context_token`、媒体解密 | **任何业务概念**（不知道"单品""搭配"） |
| `services/conversation.py` | 意图、会话状态、怎么调业务 | **任何协议细节**（不知道 `context_token`、不知道长轮询） |
| `services/*`（既有） | 自己那块的业务 | 完全不知道微信存在 |

**这条边界是硬约束**：换通道（企业微信 / Telegram / 命令行）时，`conversation.py` 一行不用改。
判据（**W4 审查后修正**）：`conversation.py` **不 `import httpx`**、不拼 URL、
不出现任何 iLink 端点名。

> ⚠️ 本文档原先写的判据是"**grep 不到 `httpx` / `token` / `ilink` 任何字样**"，
> 那是**错的**：本层要持久化 `context_token`（见 §3），它必然作为形参出现；
> 注释里也会提到这些词（那正是在声明"本层不认它们"）。
> 要守的是「**不认识协议语义**」，不是「不许出现这些字」。

## 3. `conversation_state.state` 的规格（本文档存在的主要理由）

设计文档 §13 只写了「`conversation_state` 表持久化 `context_token` 与对话状态」一句，
而 `schema.py:230` 的 `state TEXT NOT NULL DEFAULT '{}'` 是**整个多轮对话状态机的载体**。
**结构在此冻结。**

```jsonc
{
  // 最近一次给出的搭配（按展示顺序，最多 3 个 outfit_id）
  // 用途：用户回「第 2 套」「这套行」「换一套」时知道指什么
  "last_outfits": ["of_ab12", "of_cd34", "of_ef56"],

  // 最近操作过的单品（最多 5 个 item_id，新的在前）
  // 用途：用户说「这件怎么搭」时知道是哪件
  "last_items": ["it_9a8b"],

  // 待确认的录入草稿（没有就是 null）
  // 用户选了「先问一句再入库」，所以草稿先落在这里、不入库
  "pending_draft": {
    "raw_text": "深灰宽松卫衣",        // 用户原话，回显用
    "fields": { "type": "hoodie", "colors": ["gray"], "fit": "loose" },
    "unresolved": { "未识别": "带帽" },   // 归一失败的，如实告诉用户
    "at": "2026-10-05T19:39:39"         // 草稿落定时间 → 供 §3.1 ②' 的 30 分钟上限用
  },

  // 上次更新的时间（用于判断会话是否过期）
  "updated_at": "2026-10-05T19:39:39"
}
```

### 3.1 三条设计决定（都有理由，别随手改）

**① 只存 ID，不存内容。**
`last_outfits` 存 `outfit_id` 而不是整套搭配的文本 —— 因为 `outfits` 表里已经有了，
存两份就会出现"状态里的和库里的不一致"。回复时现查。

**② 会话过期 = 2 小时**（`updated_at` 超时就当新会话，清空 `pending_draft` 与 `last_outfits`）。
理由：太短（5 分钟）想一下再回就失效；太长（跨天）昨天问的搭配今天回「第一套」会关联错，
而用户早忘了是哪套。2 小时覆盖"出门前问、路上回"这个真实节奏。
⚠️ `last_items` **不过期** —— "这件怎么搭"里的"这件"最自然的指代是最近那件，隔天也成立。

**②' 草稿另有更短的 30 分钟上限**（看 `pending_draft.at`，代码里是 `DRAFT_TTL`）。
一个「要不要入库」的问题放两小时再问就没意义了；会话整体仍在 2 小时内。
> W4 审查指出：本节原先只写了 2 小时，而实现里有**两条** TTL —— 属**文档漏写**，此处补上。
> `pending_draft` 因此比 §3 的示例多一个 `at` 键（也是本轮补进 §3 的）。

**③ 一个 peer 一行**（`idx_conv_peer` 是 `(channel, peer_id)` 唯一索引）。
所以 `state` 是**覆盖式**更新，不是追加。写入时读-改-写，**必须在同一个事务里**
（否则两条消息并发处理会互相覆盖 —— 这是静默错）。

## 4. 会话状态机（第一版：纯规则，不调模型）

**为什么第一版不用 LLM 做意图识别**：高频意图（"怎么搭"、"第 2 套"、"对"）规则能覆盖；
规则可测试、零成本、结果可复现。规则不中时给明确提示，而不是猜。
（后续可加 LLM 兜底，但那时要有"分类不确定就反问"的保护。）

```
收到消息
  │
  ├─ 会话过期？ → 清 state
  │
  ├─ 有 pending_draft 且消息像"确认"（对/好/可以/ok/是）
  │     → 草稿入库 → 回复"已入库：X"→ 清 pending_draft
  │
  ├─ 有 pending_draft 且消息像"修正"（不对/是…/应该是…）
  │     → 用文本修正字段 → 回更新的草稿 → 再等确认
  │
  ├─ 命中"没得搭 / 缺什么"        → 场景 E：缺口分析
  │
  ├─ 命中"想买 / 值得买"          → 提示"这个场景在 P4"（别假装能做）
  │
  ├─ 像"描述一件衣服"（"我有一件…" / 含品类词）
  │     → 场景 C：抽属性 → 存 pending_draft → 反问确认
  │
  ├─ 像"这件怎么搭"（含"搭"/"配"，或有 last_items）
  │     → 场景 A：recommend → 存 last_outfits → 回复 3 套
  │
  ├─ 是数字 / "第 N 套" / "这套行" / "换一套" + 有 last_outfits
  │     → 反馈：写 feedback → 触发偏好更新 → 回复"记下了"
  │
  └─ 都不命中 → 明确提示能做什么（不猜、不装懂）
```

### 4.0 三条容易误读的地方（W4 审查后补）

- **判据顺序 ≠ 文档从上到下的顺序**，以实现 `classify_intent` 为准。关键一条：
  **「问搭配」排在「肯定反馈」之前** —— 否则「今天穿什么好看的」同时含
  `_MATCH`（穿什么）与 `_LIKE`（好看），会被判成 like 并**白白写一条假反馈**。
- 分支 6 的「含品类词」指**纯描述**；句子里同时有「怎么搭」时走场景 A（分支 7）。
  例：「这件卫衣怎么搭」→ **场景 A**，不是场景 C。
- 分支 7 的「或有 `last_items`」落地为：有 `last_items` 且句子里出现
  「这件 / 这条 / 这双 / 它 …」这类**指代词**时，也算场景 A（光有 `last_items` 不算）。

### 4.1 反馈的指代规则（最容易被忽略的一环）

| 用户说 | 指 |
|---|---|
| 「2」/「第 2 套」/「二」 | `last_outfits[1]` |
| 「这套行」/「不错」/「可以」 | `last_outfits[0]`（最推荐那套） |
| 「换一套」/「都不行」 | **不写反馈**，重新推荐（并排除这次的候选） |
| 「1 不行」 | `last_outfits[0]` 记 dislike |

⚠️ 回复里**每套都要带序号**（`1️⃣ 2️⃣ 3️⃣`）—— 否则用户说"第 2 套"时我们没有共同语言。

## 5. 波次与门

| 波 | 内容 | 门 |
|---|---|---|
| **W0** | 快照 + `docs/history/p3-design.md`（本文）+ 冻结 `clawbot.py` 的边界 stub | 门 1：文件集 |
| **W1** | **协议层**：扫码绑定（`get_bot_qrcode` + 轮询状态）+ 长轮询收消息 + 发消息 | **门 2：真扫一次码，确认 token 拿到、消息真能收发** |
| **W2** | 会话状态机 + 三个场景（A/C/E） | 门 3：假通道跑通全流程 |
| **W3** | 反馈指代 + 语音转文字接入 | 门 4 |
| **W4** | 双审查（**保留规格核对官** —— P3 的失败是静默的） | 门 5 |
| **W5** | 修 + 复审 | 门 6 |

**W1 是整条路的胜负手**：如果协议层跑不通（插件没灰度到 / 协议有变），
后面全是白做。所以**先把 W1 单独做完并请用户真扫一次码**，再往下。

## 6. 已知不确定项（实现时必须先探，不要假设）

| # | 不确定 | 怎么探 |
|---|---|---|
| 1 | 用户微信里有没有 ClawBot 插件 | ✅ **已确认有**（2026-10-05），且已完成扫码绑定 |
| 2 | `get_qrcode_status` 的状态字段名与取值 | ✅ 已实测（`wait` / `scanned` / `confirmed` / `expired`） |
| 3 | token 是否 24 小时过期 | 挂一天观察（目前无到期提示逻辑，只在报错后每 5s 退避重试） |
| 4 | `X-WECHAT-UIN` 是否必填、格式要求 | 现已**始终携带** `base64(random_uint32)`（按 📄 资料实现）；真机报错就摘掉 |
| 5 | 长轮询 35 秒的行为（超时返回空还是报错） | ⏳ 待真机 |
| 6 | 媒体 AES 解密（第二阶段） | 暂不做 |

**共同纪律**：本文档里标 📄（来自资料）的东西**都当"待验证"**，
实现时先发一次真实请求看响应，**别照抄资料里的字段名**。

## 7. 不在 P3 范围（明确排除，别顺手做）

- **主动推送**（定时/天气触发）→ P4（需要 `weather` 模块）
- **场景 D「我想买这件」** → P4（`purchase.py`）
- **图片打标** → 第二阶段（依赖视觉 key）
- **群聊** → 协议暂不支持单聊以外
